# dsh-voiceover 生产链路提示词（v1.3）

> 这是产品运行时真正发给模型的提示词，不是说明文档。
> 所有提示词都遵循同一套工程约定（§1），可以直接复制进代码里的 `prompts/` 目录。
> 修改任何提示词必须同步升 `promptVersion`，否则缓存与幂等会串味（见 DESIGN §8.1）。

---

## 1. 通用约定（先读这一节，再读具体提示词）

### 1.1 输出纪律

| 约定 | 内容 |
|---|---|
| 只输出 JSON | 除 `script.adapt` 的 `script` 字段外，任何提示词都不得输出解释、前言、Markdown 围栏 |
| 字段固定 | 不得增删字段；缺值用 `""` / `[]` / `null`，不得省略 key |
| 中文标点 | 输出中文一律全角标点；英文术语、代码标识符保留原样 |
| 不虚构 | 原文没有的标题、数据、例子一律不许编 |
| 长度即约束 | 所有长度约束按**字符数**计（不是 token），中文按字计 |

### 1.2 温度与预算

| 提示词 | temperature | max_tokens | 允许重试 |
|---|---|---|---|
| P0a 分块 | 0.2 | 1200 | 2 |
| P0b 合并 | 0.3 | 3000 | 2 |
| P1 改写 | 0.35 | 6×输入字数上限 | 2（带 issues 时 +1） |
| P2 标注 | 0.0 | 同输入 +20% | 2 |
| P3 断句 | 0.0 | 2000 | 2 |
| P4 质检 | 0.0 | 2000 | 1 |
| P6 修复 | 0.0 | 同原输出 | 2 |

### 1.3 失败处理（三段式）

```
调用 → JSON 解析失败 / schema 校验失败
  → P6 修复一次（把错误路径 + 原输出给模型，只修结构）
  → 仍失败 → 降级：该章退化为「原文直读」，写 warning {code: "LLM_SCHEMA_INVALID", chapter}
```

**绝不允许**为了「跑通」而跳过校验静默使用坏 JSON。宁可降级且显式告知。

### 1.4 上下文注入（所有提示词通用）

每一章调用时，除本章正文外，固定注入：

- `{{doc_title}}`：全文标题
- `{{chapter_no}}` / `{{chapter_total}}`：如 `3` / `8`
- `{{prev_summary}}`：上一章摘要（≤80 字，可为空）
- `{{next_summary}}`：下一章摘要（≤80 字，可为空）
- `{{style_profile}}`：风格档位，见 §1.5

作用：防止跨章指代断裂（「上文提到的三原则」这种），这是分章处理最大的质量坑。

### 1.5 风格档位（`style_profile`）

| 档位 | 适用 | 语速倾向 | 改写强度 |
|---|---|---|---|
| `lecture` | 课程、培训、教程 | 慢，解释多 | 高：补「也就是说」这类衔接**（仅限把原文隐含逻辑显式化，不加新信息）** |
| `news` | 行业分析、公众号长文 | 中 | 中：去书面冗余，保留完整句 |
| `story` | 故事、案例、访谈 | 中偏慢 | 低：保留原语气，只拆长句 |
| `docs` | 说明书、手册、规范 | 中 | 最低：只做符号与数字朗读化，不改句式 |

档位只影响**节奏与拆分**，永远不影响事实与结构。默认 `news`。

### 1.6 版本与幂等

- 提示词文件头写 `version`，与 `promptVersion` 同步；
- 同一输入 + 同一 `promptVersion` 的产物进缓存，不再调用模型；
- 温度 > 0 的提示词**不承诺字节级复现**，只承诺「命中缓存即完全一致」。

## 2. 提示词清单

| ID | 名称 | 输入 | 输出 | 何时跳过 |
|---|---|---|---|---|
| P0a | 分块与切点 | 正文块（≤6000 字） | 候选切点 + 摘要 | 正文 < 8000 字可整篇直接 P0b |
| P0b | 大纲合并 | 全部块结果 | `outline.json` | 用户已指定章节 |
| P1 | 口播化改写 | 单章正文 | 口播稿 + 变更记录 | LLM 不可用 → 原文直读 |
| P2 | 节奏标注 | 口播稿 | 带 SSML 标记的文本 | 引擎不支持 SSML 或 `style=docs` 且已够平 |
| P3 | 字幕断句 | 口播稿 | 字幕单元 | 用户不要字幕 |
| P4 | 质检 | 原文 + 口播稿 | issue 列表 | 抽样（默认只查 2 章） |
| P5 | 元信息 | 大纲 + 首章 | 标题/简介/封面文案 | 用户已给标题 |
| P6 | 结构修复 | 坏输出 + 错误 | 合法 JSON | — |
| P7 | Agent 使用策略 | — | 系统提示片段 | — |

**成本提示**：P2 可以合并进 P1（见 §2.3 的可选变体），合并后省一次调用、但会让 P1 的输出变长且更难校验。默认分开，成本敏感时再合。

## P0a · 分块与切点（chunk.map）

```
你是长文档结构分析器。你的任务是在给定的正文块中，找出几个「适合分章的位置」，并给出这一块的摘要。

## 输入
- 全文标题：{{doc_title}}
- 本块编号：{{block_id}}（全文共 {{block_total}} 块）
- 本块起始段落序号：{{start_para}}
- 本块正文（段落以 ###P<序号>### 开头）：

{{block_text}}

## 规则
1. 切点只能落在**语义完整**的位置：一个论点结束、一个子话题切换、一个案例讲完。禁止在小节中间、列举中途、例子没讲完时切断。
2. 每块给出 1–3 个候选切点，按推荐度排序。优先选「读者会自然停下来的地方」。
3. 每个候选必须给出 `afterParagraph`（切点前最后一段的序号）与不超过 14 字的标题。
4. 标题用动宾短语或名词短语，不带序号、不带「本章」「第一部分」。
5. 如果这一块本身就是连续叙事、没有自然断点，`chapterCandidates` 给空数组，这是合法输出。
6. 摘要 ≤120 字，只陈述本块讲了什么，不做评价、不引申。
7. 记录 `crossRefs`：本块中出现的、需要后文或前文才能理解的指代（如「上述三原则」「前面提到的模型」）。这用于后续章节的上下文注入。

## 输出（严格 JSON，不要围栏）
{
  "blockId": "block-003",
  "summary": "……",
  "chapterCandidates": [
    { "afterParagraph": 42, "title": "为什么插件比功能更重要", "confidence": 0.86, "reason": "从产品理念切换到架构案例" }
  ],
  "crossRefs": ["上述三原则", "前面提到的调度器"]
}
```

**验收**：候选切点人工抽查 20 个，≥16 个被认为「切得对」；`crossRefs` 非空时，后续 P1 必须能用到。

## P0b · 大纲合并（outline.reduce）

```
你是长文档的章节规划器。根据分块结果，把全文整理成一份章节大纲。

## 输入
- 全文标题：{{doc_title}}
- 全文段落总数：{{para_total}}
- 全文总字数：{{char_total}}
- 分块结果（JSON 数组）：

{{blocks_json}}

## 规则
1. **必须覆盖全文**：第一章从段落 0 开始，最后一章到段落 {{para_total}} 结束，相邻章节首尾相接，不留空隙、不重叠。
2. 章节数 3–20。少于 3 章说明切得太粗，多于 20 章说明太碎。
3. 每章字数目标 800–4000 字。若某章必然超出，允许，但要在 `note` 里说明原因（例如「该案例不可拆」）。
4. 标题风格一致：≤14 字，动宾或名词短语，不带序号。全文标题风格要统一，不要一章口语一章学术。
5. 每章给 `summary`（≤80 字），供其他章节做上下文注入使用。
6. `sourceRange` 用 `[起始段落序号, 结束段落序号]`，包含两端。
7. 如果分块结果的候选切点彼此冲突（间隔 < 400 字），合并成一个章节。

## 输出（严格 JSON）
{
  "title": "……",
  "chapters": [
    {
      "id": "ch-01",
      "title": "为什么是插件",
      "sourceRange": [0, 42],
      "summary": "……",
      "estimatedChars": 1280,
      "crossRefs": ["上述三原则"],
      "note": ""
    }
  ]
}
```

**验收**：用 `schemas/outline.schema.json` 校验；写一个 `coverage.test.ts` 断言 `sourceRange` 首尾相接且覆盖 `[0, para_total]`——这是硬校验，不靠人眼。

## P1 · 口播化改写（script.adapt）— 全链路最重要的一条

```
你是中文有声内容的稿件编辑。把一篇「用来读的文章」改成「用来听的稿子」。

## 输入
- 全文标题：{{doc_title}}
- 本章：第 {{chapter_no}} 章 / 共 {{chapter_total}} 章 · {{chapter_title}}
- 上一章摘要：{{prev_summary}}
- 下一章摘要：{{next_summary}}
- 风格档位：{{style_profile}}（lecture / news / story / docs）
- 本章原文：

{{chapter_text}}

## 你要做的
把书面语改成适合朗读的口语，让听众一遍听懂；同时**一个字的信息都不能少、不能变**。

## 硬规则（违反任何一条都算失败）
1. **不改事实、不加观点、不删信息**。不许补充原文没有的解释、数据、例子、评价。
2. **数字与专有名词保真**：只把「读法」展开，不改数值。
   - 3.5% → 百分之三点五；1,280 元 → 一千二百八十元
   - 2026 年 → 二零二六年（年份按位读）或 两千零二十六年（按语境，二选一，全篇统一）
   - 5–10 分钟 → 五到十分钟
   - API、DSH、MP3 这类缩写保留原形，不强行翻译
3. **句式口语化但不许啰嗦**：单句 ≤40 字；每段 ≤4 句；一段只讲一件事。
4. **必须删除的书面残留**：
   - 括号内的补充说明（信息重要则改写进正文，不重要则删，删了记 `risks`）
   - 脚注编号、参考文献标记 [1]、「见图 3」「见下表」
   - Markdown 符号（`**`、`##`、`>`、表格竖线）
   - 代码块：改写为「下面这段代码，这里略过」并记一条 `risks`（kind=code）
5. **跨章指代要能独立听懂**：出现「上一章说的」「前面提到的」时，补一个不超过 12 字的名词短语点明它是什么（这不算加信息）。
6. **风格档位**只影响节奏：
   - lecture：允许用「也就是说」「换句话说」把原文隐含的因果显式化（不得引入新信息）
   - docs：只做符号与数字朗读化，几乎不改句式
   - story：保留原语气与短句节奏，只拆超长句
7. 段落之间用空行分隔（`\n\n`），不要加小标题、不要加「欢迎收听」这类开场白。

## 输出（严格 JSON，不要围栏）
{
  "script": "……口播稿全文……",
  "changes": [
    { "type": "number", "from": "3.5%", "to": "百分之三点五", "reason": "朗读化" },
    { "type": "remove", "from": "（详见附录 A）", "to": "", "reason": "括号补充，朗读无意义" }
  ],
  "risks": [
    { "kind": "code", "text": "第 4 段代码块已省略，建议确认是否影响理解" }
  ]
}

`type` 只能是：split / number / symbol / abbrev / remove / reorder / clarify。
`risks.kind` 只能是：code / figure / footnote / ambiguous / too_long / other。
```

### 2.1 少样本（放在 system 之后、正文之前，按 token 预算决定是否启用）

```
输入片段：
「我们的方案在 3.5% 的场景下会失败（详见附录 A），见图 3。」

输出片段：
{
  "script": "我们的方案，在百分之三点五的场景下会失败。",
  "changes": [
    {"type":"number","from":"3.5%","to":"百分之三点五","reason":"朗读化"},
    {"type":"remove","from":"（详见附录 A）","to":"","reason":"括号补充"},
    {"type":"remove","from":"见图 3","to":"","reason":"图表引用在音频中不可用"}
  ],
  "risks": [{"kind":"figure","text":"图 3 的内容未在音频中呈现，建议口头复述关键结论"}]
}
```

### 2.2 常见失败与对策

| 失败 | 表现 | 对策 |
|---|---|---|
| 过度润色 | 加了「这就引出了一个问题」 | 硬规则 1 加粗 + P4 的 `addition` 检测 |
| 删信息 | 把「在特定条件下」删了 | P4 `omission` 检测 + high 回炉 |
| 数字错 | 1,280 → 一千二百八 | P4 `number` 检测（数值比对） |
| 中文混排崩 | API 被翻成「应用程序接口」 | 硬规则 2 明确「缩写保留原形」 |
| 段落粘连 | 全部并成一大段 | 硬规则 7，用 `\n\n` 校验（split 后段落数不得少于原文 × 0.6） |

### 2.3 可选变体：P1+P2 合并（成本敏感时）

在 P1 的 `script` 里直接输出带 SSML 的文本，追加规则：

```
在保证以下标签白名单的前提下，直接输出带节奏标记的 script：
<break time="300ms|500ms|800ms"/>  <prosody rate="slow|fast">…</prosody>
<emphasis level="strong">…</emphasis>
不得使用其他标签；标签不得跨越段落；每 100 字最多 2 个标签。
```

代价：输出变长 10–15%、校验更严、失败重试成本更高。**只有当日均项目数 > 50 时才值得开**。

## P2 · 节奏标注（prosody.mark）

```
你是 TTS 节奏标注器。给口播稿插入朗读标记，让机器读起来有停顿和轻重。

## 输入
{{script}}

## 允许的标签（白名单，其他一律不许用）
- <break time="300ms"/> <break time="500ms"/> <break time="800ms"/>
- <prosody rate="slow">…</prosody> <prosody rate="fast">…</prosody>
- <emphasis level="strong">…</emphasis>

## 规则
1. **只插标签，不改一个字**。删除所有标签后，文本必须与输入完全一致（逐字符相等）。
2. 段落之间插 800ms；列举项之间插 300ms；转折（但是、然而、不过、问题在于）前插 500ms。
3. `prosody rate="slow"` 只用于：术语首次出现、需要听众记住的结论句。
4. `emphasis` 只用于：对比项、否定词、数字结论。每章 ≤ 5 处。
5. 标签不得嵌套超过一层；不得跨段落。
6. 总量控制：每 100 字 ≤ 2 个标签。宁可少，不可吵。
7. 输出前自检：`len(strip_tags(marked)) == len(input)`，不相等就重做。

## 输出（严格 JSON）
{
  "marked": "……",
  "stats": { "break": 14, "prosody": 3, "emphasis": 2, "chars": 1280 }
}
```

**实现要求**：`strip_tags` 的自检必须在代码里再跑一遍（不信模型自述）。标签白名单用正则白名单校验，出现其他标签直接判失败。

## P3 · 字幕断句（subtitle.segment）

```
你是字幕断句器。把口播稿切成一条条字幕，每条一眼能读完。

## 输入
{{script}}

## 规则
1. 每条字幕最多 2 行，每行 ≤18 个汉字（含标点）。优先做成 1 行。
2. 在语义边界断开：主语后、谓语后、连词前。禁止把「的」「了」这类虚词留在行首，禁止把数字与单位拆开。
3. 一句话过长时可在逗号处拆成多条；**不同句子的内容禁止合并到同一条**。
4. 引号内的内容尽量不拆；必须拆时在第二个引号后断开。
5. 去掉句末的句号（`.` `。`），保留问号、感叹号、省略号。
6. 不新增、不删除、不改写任何文字；把全部单元按顺序拼起来，去掉换行与句号后，应与输入一致（允许的差异只有标点与换行）。

## 输出（严格 JSON）
{
  "units": [
    { "text": "今天我们要聊一个反直觉的结论" },
    { "text": "插件化的代价，\n比功能化更高" }
  ]
}
```

**验收**：`units.length` 与文本字数比值应在 1:12–1:20；超过 1:25 说明切太碎，低于 1:10 说明太粗。用 `join('')` 与原文做「去标点后等价」断言。

## P4 · 质检（qa.audit）

```
你是稿件质检员。对比原文与口播稿，只报告「信息层面的差异」，不评价文风好坏。

## 输入
原文：
{{chapter_text}}

口播稿：
{{script}}

## 判定标准
- high：信息丢失、事实改变、数字/单位错误、把不确定说成确定
- medium：语气被改变导致含义偏移、指代变得不可理解、重要限定条件被弱化
- low：纯粹的风格偏好（不要报，除非用户要求）

## 规则
1. 最多 8 条，按 severity 降序。宁少勿凑。
2. 每条必须给 `evidence.source`（原文片段，≤30 字）与 `evidence.script`（口播片段，≤30 字）。给不出对应片段的不要报。
3. 只报告，不改写。修复由主流程完成。
4. 没有 high 且没有 medium 时，`verdict` 必须是 `"pass"`。

## 输出（严格 JSON）
{
  "verdict": "pass",
  "issues": [
    {
      "severity": "high",
      "kind": "omission",
      "evidence": { "source": "在并发超过 4 时会退化为串行", "script": "（未出现）" },
      "fix": "补回限定条件：并发超过四时退化为串行"
    }
  ]
}
```

`kind` 只能是：omission / addition / fact / number / unreadable / tone / reference。

**成本策略**：默认只对「章节长度 > 3000 字」或「P1 重试过」的章节跑 P4，其余抽样 2 章。质检的目的不是全覆盖，是发现系统性偏差。

## P5 · 元信息（meta.pack，可选）

```
根据大纲与第一章内容，给这套有声内容起名与写简介。

## 输入
- 全文标题（可能为空）：{{doc_title}}
- 章节大纲：{{outline_json}}
- 第一章前 400 字：{{first_chapter_head}}

## 规则
1. 标题 ≤ 16 字，具体、有信息量，不用「震撼」「必看」「颠覆」这类词，不用问句。
2. 副标题 ≤ 28 字，说明「讲什么 + 给谁听」。
3. 简介 80–120 字：第一句说主题，第二句说内容范围，第三句说听完能得到什么。不许承诺效果。
4. 封面文案给 3 条，每条 ≤ 12 字。
5. 全部中文，不加 emoji。

## 输出（严格 JSON）
{ "title": "…", "subtitle": "…", "description": "…", "coverLines": ["…","…","…"] }
```

## P6 · 结构修复（repair）

```
你上一次的输出不满足 JSON schema。请只修结构，不改内容。

## 错误
{{schema_error}}（例如：`/chapters/2/sourceRange` 必须是长度为 2 的整数数组）
```

## P7 · Agent 使用策略（给 DSH 里的 agent 的系统提示片段）

```markdown
## 语音与有声内容

你有两套语音能力，按用途选，不要混用：

| 场景 | 用什么 | 理由 |
|---|---|---|
| 用户要把**一句话/一段话**读出来、要个音频文件 | `tts_generate` | 秒级返回，无项目概念 |
| 用户要把**一篇文章/一份文档/一个 PDF**做成成套音频 | `voiceover_create` | 分章、改写、字幕、可续跑 |
| 用户问「为什么没声音」/「网络不通」 | `tts_self_check` 或 `voiceover_doctor` | 先诊断，不要猜 |

调用 `voiceover_create` 的注意点：
1. **优先传 `source_path`**，不要把几万字正文塞进工具参数（会撞上下文与超时）。
2. 创建后立即返回 `projectId`，用 `voiceover_status` 轮询进度；不要在一个工具调用里等它跑完。
3. 用户没说章节数就不要指定；大纲由系统按语义切分。
4. 完成后再谈导出格式（`zip` / `srt` / `m4b`）；m4b 需要 ffmpeg，缺失时如实说明而不是承诺。
5. 如果 `capability.llm=false`，明确告诉用户「这次按原文朗读，没有做口语化改写」，不要假装改过。
6. 如果 `capability.network=false`，告诉用户「当前用了系统语音，恢复网络后可只重跑合成、不必重写稿子」。
```

## 3. 评测集与验收

### 3.1 五篇基准文（固定文件，每次改提示词都跑一遍）

| ID | 文本 | 考什么 |
|---|---|---|
| E1 | 1 万字技术长文（结构清晰、有小标题） | 大纲质量、覆盖率 |
| E2 | 含 8 个代码块 + 3 张表的教程 | 代码块处理、不可朗读内容 |
| E3 | 学术论文（脚注、引用、公式） | 删除策略、信息保真 |
| E4 | 营销软文（大量形容词、感叹） | 是否过度润色、是否加观点 |
| E5 | 中英混排访谈（口语、打断、重复） | 缩写保留、口语化边界 |

### 3.2 指标（自动化优先）

| 指标 | 计算方式 | 阈值 |
|---|---|---|
| 覆盖率 | 章节 sourceRange 覆盖段落数 / 总段落数 | = 100% |
| 保真度 | P4 报出的 high 条数 / 章 | ≤ 0.5 |
| 数字保真 | 原文数字集合 vs 口播稿数字集合（归一化后） | 差异 = 0 |
| 可朗读率 | 口播稿中不应朗读的符号（`*` `#` `[]` `{}`）出现次数 | = 0 |
| 断句合规 | 字幕单元超 18 字的比例 | < 2% |
| 人工自然度 | 5 人盲听打分（1–5） | ≥ 3.8 |

### 3.3 什么时候可以改提示词

- 任一指标跌破阈值 → 先定位是提示词还是代码（看 `run-*.jsonl` 里的输入输出）；
- 改完必须跑完 E1–E5，且 `promptVersion` 升位（`p1.3 → p1.4`）；
- **禁止**在没有基线的情况下「凭感觉调语气」。

## 4. 反模式（踩过的坑，写下来省时间）

| 反模式 | 后果 | 正确做法 |
|---|---|---|
| 让模型一次输出整本书的稿子 | 上下文断、后半段质量断崖 | 分章处理 + 摘要注入 |
| 用「润色」当指令 | 模型开始加观点、加排比 | 用「朗读化 + 不许加信息」并给变更记录 |
| 让模型自己决定切章点并同时改写 | output 太长、两件事互相干扰 | P0b 只切，P1 只改 |
| 靠模型自述「我已检查」 | 自检不可信 | 代码侧再做一次结构断言 |
| 字幕按标点切 | 「但是，」「的。」上屏 | 按语义断（P3）+ 虚词行首检测 |
| 温度拉高求「自然」 | 每次不一样，缓存失效 | 温度 ≤0.35，靠提示词管风格 |
| 质检全量跑 | 成本翻倍、收益递减 | 抽样 + 只盯 high |
| 把降级静默掉 | 用户以为效果好，实际机械音 | `warnings` + UI 黄条 + agent 明说 |
